Game Studio Capstone

Work as a small studio team to design, build, document, test, publish, and present an original Godot game.

What the Capstone Is

The capstone is a team-based game-jam project built in Godot 4 over several class periods. Your team will choose a small game concept, define roles, build a working prototype, publish a Google Site portfolio, complete daily progress logs, and present the finished game to the class.

The goal is not to ship a huge game. The goal is to show that you can use the parts of the Godot game system, work with others, use resources responsibly, explain your code, and reflect on your process.

Why a studio project?

Computer Programming 12 asks you to plan a realistic project, collaborate, choose resources, build and deploy a solution, document your work, test and refine it, present it, and reflect on your learning. A small game studio project lets you do all of that in one meaningful package.

Playable Godot Game

A small 2D or 3D game with player action, a challenge, feedback, and a win/lose or completion condition.

Every student logs what they did each class, what changed, what problem they hit, what AI or resources they used, and what comes next.

Game Jam Presentation

Your team demos the game live and each student answers questions about code, design choices, AI use, and their contribution.

What "done" means for this course

A game is done when: it starts, the player can interact with it, something interesting happens as a result, and it ends or loops. You do not need music, professional art, a main menu, settings screens, or save files — those are polish, not the game. Get the core loop working and tested first. Then polish if time allows.

Team Size

Teams should usually be 2-4 students . A solo project is allowed only with teacher approval. A team larger than 4 needs a very clear role plan because it becomes too easy for one person to disappear inside the group.

Group project rule

The team receives one shared product score for the game and site, but each student also receives individual evidence scores from their daily logs, code explanation, presentation answers, and documented contribution. You cannot hide inside a strong team, and you cannot carry a team without evidence.

Solo Approved Track

A solo project requires teacher approval before the proposal is submitted. If approved, the student selects Solo Approved as their track in the class tracker. All of the following rules apply.

What changes on the solo track

A solo student takes on the Coder role as their primary responsibility plus one secondary role (usually Producer or Level Builder). All scripts are entirely their own work — there is no team to share credit with, which actually makes CP12 outcomes easier to verify. Scope is adjusted downward to reflect one person working alone, but the evidence requirements are identical.

Requirement Team (2–5 students) Solo Approved
Gameplay scenes 2–3 playable scenes minimum 1 complete playable scene
Required scripts One per student based on role Player movement + one mechanic + one UI script minimum
Interactive mechanics 2+ mechanics across the team 1 mechanic (pickup, hazard, or door)
Audio Shared stretch task or Sound Designer role Optional stretch — not required
Google Site Team site — all members contribute pages Individual site — all six pages still required

Solo does not mean easier

Working alone removes the accountability of teammates. The weekly teacher check-in is mandatory for solo students. If a solo student misses two consecutive check-ins or has no log evidence for a week, they will be redirected to join an existing team.

The Five Roles

Producer

Writes the game concept, runs daily stand-ups, keeps the sprint board updated, manages scope, coordinates asset integration, and leads the final presentation.

Coder

Programs player movement, core mechanics, collision, win/lose logic, debugging, and final code documentation. The central technical role.

Artist

Creates reference images, concept art, an art style guide, all sprites or 3D materials, and delivers final assets in the correct format for integration.

Level Builder

Researches level design, sketches layouts, builds playable levels in Godot (TileMap or 3D scene), designs difficulty progression, and tests all interactive elements.

Sound Designer

Creates or sources background music and sound effects, writes an audio style guide, integrates all audio into the game build, and balances levels. Best suited for teams of 5.

CP12 code requirement — every role, no exceptions

This is a programming course. Every student must author and be able to explain at least one complete GDScript file at the game jam demo. Your role determines which script — it does not excuse you from writing one. A student who cannot explain their code during the demo cannot score above Level 2 on the Technical criterion regardless of their role.

Required Script by Role

Role Required script Key concepts demonstrated
Producer UI manager script — CanvasLayer with score label, health display, and win/lose screen logic Label.text , game state variables, signal connections, scene switching
Coder Player movement script plus at least one additional mechanic (pickup, hazard, enemy, timer) Physics loop, velocity , move_and_slide() , input, collision response

Capstone · Studio

Team Collaboration

Godot is not Google Docs. Here is how your team shares work without overwriting each other.

CP12 outcomes evidenced in this section
  • 3.1 — work individually and collaboratively to develop solutions
  • 4.3 — manage project tasks, timelines, and team communication
Why Godot can't share like Google Docs

In Google Docs, multiple people type in the same document at the same time. Godot project files — scenes (.tscn) and scripts (.gd) — are saved locally on one computer. If two people try to edit the same file at the same time and both save it, one person's work will overwrite the other's. The solution is not a special app — it is a clear rule about who owns which files.

The One Rule That Makes Teamwork Work

Each team member owns specific files based on their role. You only ever edit your own files. You never open, move, or rename someone else's scene or script. This one rule prevents nearly every conflict.

📋 Producer hud.gd main_menu.tscn ui.tscn
💻 Coder player.gd player.tscn enemy.gd
🎨 Artist res://sprites/ res://tiles/ AnimSprite.gd
🗺️ Level Builder level_1.tscn level_2.tscn hazard.gd
🔊 Sound Designer res://audio/ audio_mgr.gd music.tscn

Choose Your System

Both options work on school computers with no software installs. Choose one per team and stick with it for the whole project.

⭐ Option 1 — Simplest

Google Drive Shared Folder

Uses your school Google account. No new accounts or tools. Everyone already knows Drive.

  • No new accounts needed
  • Works on every school computer
  • Zero learning curve
  • No version history
  • Producer manually merges each class
⚡ Option 2 — More Powerful

GitHub via Browser

Free accounts at github.com. Works entirely in a browser. Gives you a real version history and looks great on a portfolio.

  • Full version history — undo anything
  • Every change has an author and message
  • Real developer skill for your portfolio
  • Students need a free GitHub account
  • A few extra clicks per class
⭐ Option 1 — Google Drive

One-Time Setup (Producer does this)

  1. In Google Drive, create a shared folder called Team [Name] Game Project
  2. Inside it, create a folder called MAIN and one folder per person: Alex-files, Sara-files, etc.
  3. Right-click the top folder → Share → add all teammates as Editor
  4. Each teammate opens the shared folder on their school computer and downloads the MAIN folder to start their local copy of the project

Daily flow — every class

1
🌅 Start of Class Open Drive → MAIN folder. Download any files that are newer than yours. Drag them into your local Godot project to replace the old versions.
▶
2
💻 Work Time Open Godot and work normally. Only touch your assigned files. If you need something from another person's scene, ask them — don't open the file yourself.
▶
3
🏁 End of Class Upload your changed files to your personal folder in Drive (not MAIN). The Producer downloads everyone's uploads and copies them into MAIN before next class.
Producer's merge job (5 minutes)

At the start of each class, before anyone else pulls: open each teammate's personal folder → download their latest files → copy them into MAIN. That's the merge. It's simple because each person only changed their own files — nothing overlaps.

⚡ Option 2 — GitHub via Browser

One-Time Setup (Producer does this)

  1. Create a free account at github.com
  2. Click New repository → name it after the game → set to Private → check Add .gitignore → choose the Godot template → click Create repository
  3. Go to Settings → Collaborators → Invite teammates by email. They accept the invite and create their own free GitHub accounts.
  4. Click the green Code button → Download ZIP → extract it → this is your local Godot project folder. Open Godot → Open Project → point to that folder.
  5. Teammates do the same: go to the repo URL → Code → Download ZIP → extract → open in Godot.

Daily flow — every class

1
🌅 Start of Class Go to github.com/[your-repo] → green Code button → Download ZIP → extract it → open that folder in Godot (replaces yesterday's copy).
▶
2
💻 Work Time Open Godot and work normally. Only touch your assigned files. If you need something from another person's scene, ask them — don't open the file yourself.
▶
3
🏁 End of Class On github.com, navigate to your file → click Add file → Upload files → drag your changed files in → write a short message like Added jump SFX → click Commit changes.
What the commit message is for

Every upload to GitHub gets a short message and a timestamp. This creates a complete history of the project — you can see exactly what changed each class, who changed it, and roll back to any previous version if something breaks. This is exactly how professional game studios work.

What to do if two people accidentally edit the same file

Stop before uploading. Compare the two versions side by side. Decide together which one to keep, or copy the best parts of each into one file. Then one person uploads the merged version. This is rare if everyone follows the file ownership rule — but it can happen during setup week before roles are fully locked in.

Which option should your team use?

Start with Option 1 (Drive) if your team is new to collaborative development — it has zero friction and you'll spend zero class time on setup. Switch to Option 2 (GitHub) if your team wants the version history or wants a professional portfolio piece. Both are valid for CP12. Solo students do not need either — your files only live on your machine.

Every Student, Every Class

Each student completes one dev-log entry before leaving class. Teams may discuss the entry, but each student writes their own. You submit through the class Daily Dev Log form — the teacher will share the link with you on day one.

How the automated system works

1. Teacher shares the form link — bookmark it or find it on your class page.
2. You fill in the form before leaving class each day (about 5 minutes).
3. Your submission auto-updates the Class Tracker — Today Log Status changes to Complete, AI Log Status updates automatically based on your answer, and if you report no blocker the tracker clears it.
4. Your responses appear in the Dev Log Responses tab inside the Class Tracker spreadsheet — your teacher can see every entry.
5. Link or embed your responses on your Google Site — go to Daily Dev Logs page on your Site and embed the response spreadsheet so it stays current.

Daily Dev Log Prompt

  1. What did I work on today?
  2. What changed in the game, site, art, level, sound, or code?
  3. What evidence did I create today? Link a screenshot, code snippet, commit, or site update.
  4. What problem or blocker did I hit?
  5. How did I try to solve it?
  6. Did I use AI today? If yes, paste the prompt or summarize the exact help.
  7. What is my next task?
  8. Confidence check: green, yellow, or red?

AI use rule

You may use AI to explain, debug, suggest approaches, generate examples, or help with wording. You may not submit AI-generated code that you cannot explain. If you cannot answer questions about the code, it does not count as your work.

AI Log Requirements

Every AI use entry must include:

  1. The tool used
  2. The prompt or a clear summary of the prompt
  3. What the AI suggested
  4. What you accepted, changed, or rejected
  5. How you tested it
  6. What you now understand better

Good AI Prompt Pattern

I am a beginner Godot 4 student. My team is building a small 2D platformer. Explain how to make an Area2D spike damage a CharacterBody2D player. Use simple GDScript and explain each line. Do not add extra systems beyond health, damage, and invincibility.

Debug Prompt Pattern

Here is my Godot error and my script. Help me understand what the error means. Ask me one question if you need more context. Do not rewrite the whole script; show the smallest fix and explain why it works.

Resource Evaluation

When using a book, manual page, tutorial, or AI answer, students should ask:

  • Is this for Godot 4, not Godot 3?
  • Does this match my node type: 2D vs 3D, Area vs Body, Control vs Node2D?
  • Can I explain the code in my own words?
  • Did I test it in my project?
  • Did I record the source in my Google Site?

The Three Tracks

Track A — 2D Platformer

Extend your PL1–PL3 foundation into a complete level-based platformer.

  • Multiple connected levels or one large scrolling level
  • Animated player with at least 3 animation states
  • At least one type of hazard (spike, enemy, pit)
  • Collectibles with a score or progress counter
  • Win / lose condition

Track B — 3D Exploration

Extend your 3D1–3D3 foundation into a collectathon or exploration game.

  • 3D environment with distinct areas or rooms
  • CharacterBody3D player with full movement and jump
  • Multiple pickup types or objectives
  • At least one interactive element (door, enemy, switch)
  • Win / lose or end-state condition

Track C — Open Concept

Design something outside the platformer/exploration box — with teacher approval.

  • Examples: top-down shooter, puzzle game, tower defence, rhythm game, racing game
  • Must use Godot 4 and at least two of: physics bodies, signals, timers, UI, scenes
  • Must have a clear player action, consequence, and win/lose state
  • Scope must be approved before you start building — book a teacher check-in

Minimum Project Requirements

Every submission — regardless of track, team size, or demo format — must meet all of the following. A project missing any item is incomplete and cannot receive a passing grade, no matter how polished the rest is.

Requirement Why it cannot be skipped
Player movement with physics — CharacterBody2D or 3D, gravity, is_on_floor() , move_and_slide() The foundation of any Godot game. A project without it has not applied the core course skills.
At least one interactive mechanic — pickup, hazard, enemy, or door using Area2D/3D and signals Requires demonstrating signals, node communication, and queue_free() — essential CP12 outcomes.
Score or health tracked in a variable and displayed on a HUD — CanvasLayer + Label + script Proves the student can connect game state to a UI element — a distinct CP12 programming requirement.
A working win condition AND a working lose condition Without both, the game loop is incomplete. A game that only ends one way is not finished.
At least 2 scenes — one gameplay scene plus a win/lose screen or title screen with a scene transition Proves the student can manage multiple scenes and use change_scene_to_file() .
Daily dev log entries for every project class session The timestamped evidence trail. Thin or missing logs indicate the work happened in a rush, not over time.
Each student can explain their required script line by line The CP12 programming outcomes gate. A student who cannot explain their code cannot score above Level 2.
Why these requirements prevent a two-class submission

A student who genuinely implements player physics, an interactive mechanic, a HUD, win and lose conditions, and a scene transition — with a daily log entry for every class — has done roughly 8–12 hours of focused Godot work. That cannot be faked in two classes. The logs are your strongest protection: if entries are thin for the first three weeks and everything appears in the final week, that pattern is the conversation.

The #1 capstone failure mode

A student spends 80% of the project time on one complex feature — custom AI, procedural generation, an inventory system. The core game loop never gets built. A simple, complete, playable game earns a higher grade than an ambitious, half-finished one every time.

The Minimum Viable Game (MVG) Test

Before adding any feature, ask: "Is this the game without it?"

  • Without player movement — not a game. Required.
  • Without a win/lose condition — not a game. Required.
  • Without sprite animation — still a game (colored rectangle works). Nice to have.
  • Without a main menu — still a game. Polish.
  • Without sound — still a game. Polish.
The "build in order" rule

Always build in this order: (1) Player can move, (2) Player can die / lose, (3) Player can win, (4) The whole loop works start to finish. Only then add anything else. If you add art before the loop works, you have a pretty demo that is not a game.

Scope Reduction Checklist

If your proposal has features in the "Out of scope" or multiple "Stretch" rows, use these cuts:

  • Dialogue → description label. Instead of a dialogue system, use a static Label node that shows a message when the player enters an Area.
  • Multiple levels → one long level. One large scrolling TileMap takes a fraction of the time of a multi-scene level system.
  • Procedural → hand-crafted. Paint your level by hand. It is faster, more controllable, and you know it works.
  • Complex enemy AI → patrol or static. A back-and-forth patrol is fully satisfying as a hazard. Chase AI is a stretch goal.
  • Inventory → score counter. A simple integer score variable replaces 80% of what an inventory does for gameplay feel.
Scope self-check — do this before starting to build
  • Each of my three required features is in the "Core" row of the table above
  • I can explain exactly how I will implement each feature (which nodes, which scripts)
  • I could build a rough version of each feature in one class period if I had to
  • My stretch goal is clearly marked and I will not start it until the core is done and tested

Evidence Types Reference

S

Screenshot

Game running in a state that shows a specific feature working. Label every screenshot with what it shows.

E

Written response

2–5 sentences answering a specific question about a design or technical decision. Be specific — "it works" is not an explanation.

C

Annotated code

A script with comments on every non-obvious line explaining what it does and why. The comments must be written by you — not copied from a tutorial.

D

Debug log

One or more entries describing: what broke, what you tried, what worked. Honest debugging logs show more skill than "it worked first try."
